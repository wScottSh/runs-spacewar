# RUNS: the intent, as the Spacewar conversion found it

This is a working note from the conversion of Spacewar! 3.1 to RUNS. It records what the conversion has found, and why, and checks each claim against the running original. `../.github/CONTEXT.md` (cited below by line as EGS CONTEXT.md; not this repo's `CONTEXT.md`) is the EGS vocabulary: where this note disagrees with it, it governs, unless the user has said otherwise more recently.

## What RUNS is for

RUNS exists so that a game's rules outlive the machine they were written for. The source is plain text that anyone can read, run, and change, and that any future runtime can rebuild into the same game.

This repo makes Spacewar's **conversion**: the reference for the game, rewritten into RUNS with the game exactly the same, not a Port and not a Variant (EGS CONTEXT.md, Conversion). The rules are pure and separate from the presentation, and the whole original presentation is still there. **The oracle is the binary**: the RUNS source, compiled with the PDP-1 declarations, rebuilds the original image byte for byte, and only that proves every input. The work is the **process**, documented so it repeats for every game, as automatable as possible; Spacewar is where it gets worked out (`../runs-spec/README.md`, What the work is for).

Five requirements follow from that purpose:

1. **The game is converted exactly, warts and all.** Every sequence of inputs from power-on must give the same game. That includes every glitch play can reach, because a glitch is part of the game. A re-release of Super Mario 64 without the backwards long jump would not be Super Mario 64. A conversion never changes the game to fit RUNS. Where RUNS cannot yet say what the game does, RUNS grows.
2. **The source is the game.** Its Rules region is deterministic and each Processor is total (EGS CONTEXT.md, Network), so a faithful runtime gives the same results under any evaluation order. The same results on another machine also need the game's own numeric types. The arithmetic is a rule of the game, so every RUNS game declares it, converted or born in RUNS, and another arithmetic is another game (EGS CONTEXT.md, DIGS); this conversion defines its `word` type. Nothing about the game may live only in a binary.
3. **Every rule can be swapped.** A rule is replaceable only if its whole contract is visible. A Processor's contract is its inputs and outputs, and nothing else; the Network wires each one to a Record Field, and the Processor knows nothing of the Records on the other end (EGS CONTEXT.md, Processor and Network). A hidden channel, such as a register left set, a shared scratch word, or a patched instruction, would break every swap. That is why all data flows through Records. How finely to split the rules is convention, not compliance: a monolith that passes every test vector is the game (EGS CONTEXT.md, Processor). This conversion chooses to split them.
4. **The structure is visible.** Which values flow into which rules, and the conditions under which rules fire, are rules too. The Network shows them as wiring and guarded arcs, where anyone can see them and change them. Its wires and guards state the order of execution (EGS CONTEXT.md, Network).
5. **Variation is native.** A house rule is a Variant: an edit to one Processor or one wire of the Network, not a modified copy of the program (EGS CONTEXT.md, Variant).

## The three parts

- **A Record** is anything the game remembers. Examples are the object table, the random number, the frame's time budget, and the tunables. There is no separate category for global data. Spacewar's Records hold one value or a fixed-size collection; EGS CONTEXT.md does not fix the size, and a `state:` list may grow each tick (EGS CONTEXT.md, Record and Network). Only a Processor changes a Record: it takes the value out, computes, and may put the result back in the same place. The wires and guards order any two Processors that touch one place; the random number's values pass through one place in wired order (EGS CONTEXT.md, Record and Network).
- **A Processor** is one rule. It holds no state. It declares its inputs and outputs, and the Network wires each to a Record Field; a Processor knows nothing of where its inputs came from or where its outputs go (EGS CONTEXT.md, Processor and Network). Inside its body it may use any number of intermediate values, but the body's semantics are single-assignment dataflow: a reassignment is a new version, and a loop is a bounded fold (EGS CONTEXT.md, Processor). Purity holds at the boundary: what the Processor does is a function of its inputs. Each Processor is one `.runs-prim` file with `in`, `out` and `inout` lines and names no Record.
- **A Network** is the game's skeleton: the explicit bipartite wiring of Records to Processors, a colored Petri net (EGS CONTEXT.md, Network). Values flow Record to Processor to Record, never Record to Record and never Processor to Processor. It writes nothing. A guard sits on an arc, reads a precomputed fact a Record holds, and computes nothing on it; a condition that needs arithmetic is a Processor writing a Record, which the guard tests (EGS CONTEXT.md, Phase / Dispatch / Guard). The guards of one choice form a complete partition, exactly one true, and an open-typed discriminant needs an explicit `else` arc (EGS CONTEXT.md, Phase / Dispatch / Guard). The only unbounded loop is the game itself, tick after tick; every loop within a tick runs through a counter that counts down (user, 2026-11-14). The wires and guards state the order of execution, and any order they allow gives identical results (EGS CONTEXT.md, Network).

  Spacewar writes every Network as a network file (`runs/**/*.net`): places, transitions and arcs. The arcs and their guards state the order, the original's order. Moving the collision test into its own phase after the calc routines changes 294 of 300 frames, so that order is a rule and the arcs carry it (`runs/frame/active_object.net`). Every guard set on a place is a partition, closed by `when else`.

Every Record is one of three kinds: the game's, the interface's, or the presentation's. `game` marks a Rules-region Record, `presentation` a Realization-region one, and `interface` a boundary Record. A Processor touches the game and the interface, or the presentation and the interface, never the game and the presentation. The Rules/Realization split is the enduring-games pattern, a convention of `runs-library` and not a primitive of RUNS (EGS CONTEXT.md, Processor); this project enforces it as its own rule. [Game, interface, and presentation](#game-interface-and-presentation) says why.

The topology is a Petri net. Records are the places and Processors are the transitions. No value flows from one transition straight into another. An earlier draft had a fourth kind, the function, which took words and returned words. A Processor called it, so a value went from one rule to another as a call and a return, with no place in between. This project counted that as a break in the topology and removed functions. A Processor never calls another Processor: Processors connect only through Records, by the Network, and composition is bundling, each bundle its own network file (EGS CONTEXT.md, Network). The user: "The network is what should be connecting them, not the processor, not the record" (2026-11-11). The source has no Processor call. The only calls in it are the word's own operators, such as `rcl`, `scr` and `popcount`.

A top Network is one nothing fires; it names the boundary Records with `requires:` (what the world writes before a tick) and `produces:` (what it reads after), as EGS CONTEXT.md, Boundary Record, does. Spacewar has three: `tick` (`runs/game/tick.net`), fired once a tick, and the two start Networks, one of which the host fires when the operator starts the machine. `requires:` also still states a precondition in two files (`requires: slot < 2`).

A field with no initial value is unknown until the game sets it or the world gives it. That is how the source says what comes in: the console's switches, and the words core held at power-on. Reading a field while it is unknown is an error. A top Network whose routines read a Record with such a field names it under `requires:`.

The halt that shows the scores between games ends a tick: `wait_for_operator` sets `pause.phase` to `scores_shown`, and the next tick is the operator's answer (`after_scores`). Nothing computes between ticks.

The evaluator in `tools/runs.py` enforces the rules of today's source before anything runs. A Processor's declarations match its body, in both directions: it declares each Record its body reads (`reads:`) or writes (`writes:`, which lets it read the Record too), each once, and each Record it declares is one its body reads or writes. A `jump` may touch whatever the instructions the program builds name. A Record that the game's Processors write and nothing in the game reads leaves the game, so the top Network declares it under `writes:` (`lights`). Each expression's type is checked: a number (a word or a count), a condition, an instruction, a member of an enum, or a pair; a member where a number goes, or an instruction where a word goes, is an error of the source, not of a run. A routine that fires itself is an error. A call of anything but a word operator is an error. A Processor that fires a routine is an error. A Network with `let`, `set`, `emit` or `return` is an error, and so is a Network loop without a guarded exit. So are a `break` or `continue` outside a loop, a parameter or local the routine never reads, a number that does not fit a word, a constant slot past its collection, a compare of two constants, and an ordering compare (`<`, `<=`, `>`, `>=`) with anything but 0 on its right, unless its left is a parameter or a counted loop's variable (`requires: slot < 2`). A top Network, or a Network that states a contract, must declare each stream its Processors write and each Record they share with Processors outside it, and a top Network must declare each Record with an unknown field that it reads. A Processor that nothing fires shares nothing at run time, so it does not count: the tunables the spaceship executes wait in the source for the spaceship. While the game runs, a Processor that reads or writes a Record it did not declare is an error, and so is reading an unknown field. Code a Processor runs with `jump` goes through the same contract, word by word. A Record with no kind is an error, a Processor that touches a presentation Record and a game Record is an error, so is a presentation Processor that writes an interface Record, and so is a guard that reads a presentation Record over a game routine.

## Game, interface, and presentation

Games outlive their hardware only if the presentation can be removed and replaced whole, with no change to a rule. Presentation is the screen, the sound, the controls, the pacing, and the machine underneath. It can be rebuilt for each platform. The game cannot.

The separation is in the Records. Each Record is one of three kinds (`game` a Rules-region Record, `interface` a boundary Record, `presentation` a Realization-region one):

- **Game**: what only the rules use. Fuel, the random number's state, angular momentum, the collision radius.
- **Interface**: what the game and the presentation share. The game writes what there is to show, such as positions, headings, and the random numbers the drawing uses. The world writes what comes in, such as the control word, the sense switches, and the words core held at power-on.
- **Presentation**: what belongs to one platform. The pen, the compiled outlines, the planetarium's window, the frame's time budget, the scope's points.

A Processor that touches a presentation Record is the presentation's, and every other Processor is the game's. This project's loader enforces three rules; they are this project's, not RUNS law (EGS CONTEXT.md, Processor). A presentation Processor touches no game Record. It writes no interface Record, because only the game and the world write the interface. A guard that reads a presentation Record guards only the presentation's routines. In Petri net terms, the presentation's transitions take nothing from the game's places and give nothing to them, so deleting the presentation's transitions leaves every firing of the game's the same.

The two regions are joined only by boundary Records, and the wiring states the order (EGS CONTEXT.md, Processor and Network). The Network fires both kinds in one order, the order the game needs and the original ran. Deleting every presentation Processor and every run of one leaves the game. A new platform supplies its own presentation Processors and Records against the same interface. EGS CONTEXT.md specifies no language for a presentation Processor's body (EGS CONTEXT.md, Processor); this conversion writes Spacewar's in the RUNS source. A Port swaps the Realization Processors wholesale and leaves the Rules Processors and boundary Records untouched (EGS CONTEXT.md, Port); how a platform's Processors attach to the wiring is open.

What decides a Record's kind is what its values reach, not what the code was written for. A value is the game's if any rule can observe it. The game touches the machine in only four ways:

1. **A value comes in**: the controls, a clock, the network, the contents of core at power-on. It is an interface field with no initial value.
2. **A value goes out** to the presentation. It is an interface field the game writes.
3. **The machine computes something the rules then read.** The PDP-1 wraps a sum around, a video chip latches a collision, a draw routine works out where a sword is. That computation is a rule of the game, and it moves inside the game. Ocarina of Time's `Player_PostLimbDrawGameplay` (`src/code/z_player_lib.c:1657` in the decomp) computes Link's body part positions and his sword's collider quads from the draw matrices, so part of its drawing is gameplay.
4. **Timing**: how long a frame takes, which thread ran first. Where the game's state depends on it, it becomes a rule (Spacewar's `cycles` estimates are one: they set how long an explosion lasts) or a value that comes in.

Only the third could widen the interface, and it is always resolved by moving the computation into the game. So the interface grows in data, such as a longer list of points, but never in kinds of thing.

Spacewar's original code mixes the two in single routines (read in the C lift, `lift/`). Each mix is a split to make:

- The central star is presentation, but it draws two random numbers each frame (`central_star` and `star_line`, `runs/heavens/central_star.net`, `runs/heavens/star_line.net`) from the generator that also decides hyperspace jumps and whether a ship survives breaking out (`lift/objects.c:117`, `:126`, `:167`). Sense switch 6, which turns the star off, changes hyperspace. The two draws are the game's; the line drawn from them is the presentation's, and it reads the numbers from the interface.
- The explosion's dots draw two random numbers each (`lift/objects.c:55-56`). The draws are the game's; the dots are the presentation's.
- The exhaust flame draws a random number of dots, and each dot burns a unit of fuel (`lift/spaceship.c:232`, `:243`). In the original one loop does both. The source splits them: `flame_dots` is a loop bundle whose counter is the flame's dots; each pass fires `burn_fuel`, the game's, and `plot_flame`, the presentation's (`runs/spaceship/flame_dots.net`).
- The ship outlines and the Expensive Planetarium are presentation. The planetarium draws no random numbers (`runs/heavens/expensive_planetarium.net`).
- The spaceship draws its outline by walking strokes. At each new game the outline compiler decodes each ship's outline into strokes in `outline_code` (a step, a store or restore of the pen, an end), which the declarations lay out as code in the free core after the object table. Each frame the spaceship sets the `pen` and walks its strokes (`draw_outline`), leaving the pen at the ship's tail, where the exhaust flame starts (then `after_outline(slot)` in `runs/spaceship/accelerate.net`). The walk's other effects are the points, the position it stores and restores (`pen.saved_x`, `pen.saved_y`), and `pen.side`, program flag 5, which it sets before it reads it and which nothing in the game reads (the planetarium clears flag 5 before it reads it, `oracle.lst` 570). Compiler, strokes, walk and pen are all presentation. Just before the jump the spaceship plots a dot at the center at intensity 0. On the PDP-1 that dot asks the display for the completion pulse the outline's first point waits for.
- The torpedo's start was computed through the pen: `stx = sx1 - ssn`, where `sx1` is where the outline starts. It was the one place the spaceship's rules read a presentation word, as the deleted copy below shows. Split: `aim_nose` (the game's) computes the ship's nose and the torpedo's start from it, and `aim_outline` (the presentation's) starts the pen at the nose. The declarations keep the nose in the pen's words (`[share]` in `pdp1/spaceship.toml`), so the image does not change. Checked (before the strokes): a copy of the game with the outline, the pen, the exhaust's dots, the outline compiler, `outline_code` and `type insn` deleted matches SIMH on every game Record over 1,000 spaceship calls, and a planted fuel defect is caught.
- The spare-time loop is pacing. `begin_frame` sets the frame's budget, `charge_time` and `spare_time` alone use it, and nothing in the game reads it after (`runs/frame/begin_frame.runs-prim`, `runs/frame/spare_time.net`; inferred from the converted slice, not yet from the whole game).

An earlier version of this note kept presentation code where the original runs it and only said which of its effects the game must keep. That left Processors that write both fuel and the display, so no platform could replace the presentation without touching a rule. The kinds replace it. Every Record of `runs/` has one, and the loader enforces the rules on every program: an untyped Record or a mixed Processor does not load. `tools/check_purity.py` reads source the loader refuses and lists each impurity; it reports 0.

### Spacewar's boundary so far

The three top Networks (`runs/game/tick.net`, `runs/game/start_with_test_word.net`, `runs/game/start_with_control_boxes.net`) declare what crosses between the program and the world. `console`, `score` and `controls` are interface Records the world writes, and `display` is the presentation's.

- **What comes in.** `console`: the test word switches, the control boxes, and the six sense switches (1, 2, 3, 5 and 6 the spaceship's; 4, which turns the planetarium off, the heavens'; 6 the central star's too), each a field named for what it does when on. `score`: the two scores and the games left in the match, whose starting values are what core held at power-on. Which start Network the host fires is the operator's start address, 4 or 5. Each of these is a field with no initial value. `controls`: which device the control word comes from, the operator's choice of start address, made before the first frame. `outline_code`: the outlines' strokes. The tape does not load them, so they have no initial value, and the start's new game decodes them before the first frame; the frame declares them as it declares `controls`.
- **What goes out.** `display`, the points the scope plots. `scoreboard`, the scores the halt between games shows on the console lights. `lights`, program flags 1 and 2, which light for the ship that survived a game and which nothing in the game reads.

The control word is the spaceship's input. The start Network sets `controls.source`, and each spaceship fires the `control_word` Network once a frame, which reads the test word or the control boxes from it.

## Exactness, glitches, and the machine

A glitch is one of three kinds, by what it reads.

1. **A logic glitch** is the game's own logic, such as the backwards long jump. A verbatim conversion keeps it with no extra work. Spacewar has one: the previous control word is never stored, so with sense switch 3 on the fire button always counts as newly pressed (`lift/spaceship.c`, the torpedo code). The conversion keeps it (`runs/spaceship/trigger.runs-prim`).
2. **A layout glitch** reads past an array, through a stale pointer, or one kind of object as another: DOOM's `spechit` overflow, Ocarina of Time's stale reference manipulation. In those states the rule is whatever lies next in memory, so the layout is part of the game. Where play reads the layout, the RUNS source states it.
3. **A machine glitch** runs data as code, or jumps into the middle of a routine: arbitrary code execution. On that path the rule is that the machine runs those bytes. Exactness means the original machine's instruction semantics are part of the game, used only where play reaches them, and the original code bytes are part of the game's data.

These share one piece: a description of the original machine. The game's own number, 18-bit ones' complement, is not part of it: that arithmetic is a rule of Spacewar, declared in the RUNS source (`type word`, `runs/spacewar.runs`), as Yahtzee's die has six sides. Where play reads the layout, the description supplies the layout. Where play runs into machine behavior, it supplies the instruction semantics. The rest of the game is RUNS.

The declarations for a target machine hold only the choices play cannot observe. Where the game states a layout, the declarations follow it.

A halt or a hang the original reaches is a rule, not an error. Spacewar halts when a ship fires and the object table is full (the `hlt` loop after the search for a free slot, `stop` in `launch_torpedo`). A loop bound or a `requires` that fails in the evaluator means the conversion is wrong, never that the game may do anything. A `requires:` is a precondition, as a loop's bound is: it states which firings the conversion is for (`slot < 2`: a ship's slot), it compiles to nothing, and deleting it changes no firing it lets run. It is not game logic, so no declaration or image can catch its deletion. The evaluator checks it at every firing of every check against SIMH, and `tools/check_compiled.py` shows each one stops some firing and leaves every other the same. EGS CONTEXT.md calls this a precondition, a DIGS boolean a Processor declares, discharged by the guards and checked by tooling (EGS CONTEXT.md, Precondition), and keeps the keyword `requires:` for inbound boundary Records (EGS CONTEXT.md, Boundary Record). In two network files `requires:` still states this precondition, so the keyword has two meanings.

Each loop in the source is written as a loop bundle: a counter set before the loop starts, one token taken per pass, ended when the counter reaches its end or a guard stops it (a network file with a `counter` line). Every loop must be bounded by something; the counter is the rule for the whole graph, and a loop need not sit in a bundle (user, 2026-11-14); the loader reads only the bundle form so far. Which counters are shown to hold for every input, and how the gate judges a changed counter, is not yet restated for loop bundles (`todo.md`).

Which Records need a layout stated, and where play runs into the machine, is a fact about play, not a guess. `tools/reach_oracle.py` measures it.

## Where play reaches the machine in Spacewar

It names every data access by the Record field or label it lands in, and lists each site where play depends on the PDP-1 rather than on a stated rule. It checks itself: its copy of core matches SIMH's at the end of every scenario, and its model of every add, subtract, shift and rotate (5.97 million of them) matches the AC SIMH shows after each. The full report is `docs/reach-oracle.txt`.

The head of the tape also holds words that belong to the machine and its operator, not to the game. Each was weighed by what play can observe:

- **The sequence break words (0-3) and the flush (`sbf`).** Play never raises a sequence break: the tape never executes `esm` (no `720055` in `oracle.lst`), so a break can happen only on a machine another program left in sequence break mode before the game ran. The lift's frame check runs none of these words. They are layout, and the flush is code the PDP-1 back end in `runsc` emits.
- **The start vectors at 4 and 5, and the control word routine slot at 040.** Starting at 4 or 5 chooses whether the control word comes from the control boxes or the test word switches, and the slot is where an operator builds a private control word routine. The two starts also differ in play: 5 goes to `a`, which reads the game count and the scores core held at power-on, and 4 goes to `a6`, which sets the game count from the test word first. (An earlier note here said they differ only in the control word's device; the listing says otherwise, lines 756-762.) So the start address is an input: the host fires `start_with_test_word` or `start_with_control_boxes`. Which address fires which is the console's, presentation like the sense switches and the lights, and `pdp1/devices.toml` states all of them in one place. The vectors that jump there, and the slot, are layout.
- **The tunables' fixed low addresses.** They sit there so an operator can change them from the console between games. In RUNS that change is an edit to a Processor or a field, a house rule, so the addresses are layout. The values are rules: the instructions are Processors in `tunables.runs-prim`, the numbers are fields of the `tunables` Record.

The PDP-1 declarations lay all of them out (`pdp1/tunables.toml`), and `runsc` emits the machine's words as the PDP-1 back end, the way it emits `jda`.

## How the original's routines map

The original passes values between routines in AC and IO, and that is what had made functions look natural. Each of its three ways of sharing a rule now becomes Processors and places. The shapes below map the original to the source as it stood before network files; `todo.md` lists restating them against the network files.

- **A subroutine** (`jda sqt`) is a Processor over the routine's own words. `jda` leaves the argument in the entry word `sqt`, and the routine leaves the root in `sq2`, so `square_root` reads `square_root_call.entry` and writes `square_root_call.root`. The scratch words `sq1` and `sq2` are fields of the same Record, because they are the routine's places in the original too.
- **A tunable executed with `xct`** (`the`, `hd2`, `hd3`, `hr1`, `hr2`, `tlf`) is a Processor of its own. What it takes from AC and IO and what it leaves there are fields of the `handoff` Record. A routine that executed one becomes a Network: a Processor sets the input, the tunable fires, and a Processor uses the output. An operator can still patch the rule and not only the number.
- **A subroutine that calls another** (`imp` calls `mpy`) is a Network. A Processor sets the callee's Record, as the caller's AC and the word after its call would, the callee runs, and a Processor reads the callee's results. The word after a call (`jda mpy / lac b`) is the callee's argument by name: the callee executes it each time it reads it. No caller in Spacewar names a word the callee writes, so it is a field the caller sets once (checked against every call site in the listing).
- **A skip return** (`dvd` and `idv` return one word further when the quotient fits) is a result the caller reads, so it is a Record field: an enum, `division`, whose members are the two outcomes. The declarations say which member skips.
- **Two entries into one body** (`idv` shifts its dividend and jumps into `dvd`) are a Network that runs the first Processor, then the shared routine. That the second is entered by a jump past its entry word is the declarations'.
- **A loop with two entries.** `sin` enters its reduction loop at `si1` (add 2 pi) when the angle is negative and one word later when it is not, and the loop's last jump goes back to `si1`. Structured code cannot enter a loop in two places, so the RUNS states `if a < 0: a = a + 2 pi` before the loop and ends the loop's body with the same statement. The declarations lay the two out as one (`loops = "exit first"`); the image is the original's.
- **A macro** (`random`, `diff`) is a Processor too. `random` takes `random.number`, steps it, and puts it back. `diff` reads its acceleration from `handoff.acceleration` and moves one axis of one object, so it is two Processors, `inertia_x` and `inertia_y`. It leaves the new position in AC, and the torpedo takes it up from there, so the position goes out through `handoff.position`. A loop that runs a macro moves up into the Network. The explosion's dot loop is the case in this slice.
- **A register a later rule reads without setting.** The explosion clears IO once (`cma cli`) and its dots shift each new random number in on top of the last dot's y; hyperspace shifts its draw in on top of whatever the main loop left in IO. Each IO is a `handoff` field the rule reads, as the original reads the register. The shifts push the old value all the way out, so it never reaches a Record or a point.

`handoff` holds only values that the original carried in a register from one rule to the next. Each field names the register and the instruction in a comment. A value that a Processor computes and uses itself stays a local. A word that the original keeps in core between two rules is a Record field named for what it means, such as `explosion_count.particles` (`mxc`).

Splitting a routine at each macro or tunable leaves its skips in the Network. Each guard tests what the original's skip tests. `count i ma1, tc1` becomes `run count_down(slot)` followed by `if objects.counter[slot] >= 0:`.

The main loop and the game control add four shapes:

- **A label that several places jump to** (`a`, `a4`, `a5`, `a6`, `a2`, `ml1`) is a Network of its own, and each jump is a `run` of it as the last thing a branch does. The declarations lay each one out as a block, and pdp1cc drops a jump to the block that follows.
- **The main loop's own jump back to `ml0`** is the end of a firing: the host fires the frame again. The declarations name the frame as the Network the PDP-1 repeats.
- **A halt that waits for the operator** is a Processor that emits what it shows (`runs/game/post_scores.runs-prim`), and the end of a tick: the next tick is the operator's answer (`pause.phase`).
- **The cursors' walk** is `for slot in 0 .. 026`, and the comparison loop inside it is `for other in slot + 1 .. 027`. Which cursor points at which field, which instruction holds it, and how the walk steps them are the declarations'.

The spaceship adds six:

- **A program flag that one routine sets and tests across its calls** (flag 6, the rocket fires) is a Record field, `spaceship.rocket`, an enum. The declarations hold it in the flag.
- **A jump into code the program generated, which jumps back** (`sp5`, the compiled outline) is a walker, `draw_outline`, over the strokes that code holds, and then a run of the Network the code jumps back to. That the walk is a jump through `sp5` into code is the declarations'.
- **A label several branches of one routine jump to** (`bsg`) is a Network that each branch runs as its last thing. The compiler lays it out once, where the last branch runs it.
- **The search for a free slot** is a Network loop over a field that holds a slot, `launch.slot`, that ends in `stop` when the table is full. The declarations keep the field in the search's cursor and builds the new torpedo's cursors from it.
- **A store of an address part** (`dap`) keeps the rest of the word: `set objects.cycles[launch.slot] = objects.cycles[launch.slot] & 0770000 | 020`.
- **A scratch word reused for a second meaning**: the ship in the star counts its wait in `\ssn`, the outline's first step. The RUNS source uses the same field, `pen.down_x`, as the original does. Nothing reads it before the next ship sets it.

The outline compiler adds the shapes of code that writes code:

- **Code the program writes, then runs** is a collection of commands and a walker over it: `outline_code.stroke`, an enum, which the compiler writes one stroke a direction code, and `draw_outline`, which walks a ship's strokes each frame, an if-chain arm a member. The declarations hold the collection as code (`held_as_code`, the run form of `docs/rules/held-as-code.md`): each slot's words are its member's arm, which `runsc` compiles as a `TEMPLATE` and `pdp1cc` compiles to words with its ordinary selector, and the slots lie end to end; a write of a slot stores its member's words (`LAY_OUT`), and the walk is a jump into them. The source holds no instruction. Checked: `tools/check_outline_compiler.py` encodes the evaluator's strokes as those words and compares them with SIMH's `oc`, word for word.
- **A jump inside the code to a place the compiler chose** (the end's jump back to the nose, `ocm`) is a field that holds a slot, `outline_code.back`, which the walker jumps to (`set at = outline_code.back[at]; continue`), copied from `outline_compiler.start_over`, set where the nose is written. The declarations hold both as code (`held_as_code`): the jump to that slot, `dap ocm`, then `ocm` copied whole.
- **A position in the code** is a word that holds a place in a collection (`outline_call.code`, `ships.outline`). The declarations keep it as the address of the slot's words (`[into]`); the RUNS source never says where the code lies. Checked: `tools/check_spaceship.py moved` has SIMH's compiler lay the outlines out from 05000 instead of right after the table, and every call still matches.
- **How the compiler lays a stroke's words out** (`ocs` laying out the swap twice from IO, `comtab` and `oce` sharing a step's last words, `ocd` laying out every arm's last word once, `ocn` built for the end's jump past the return) is the declarations' layout, which the source does not state: a store routine (`[[place]] store`, `times`, `loaded`), pdp1cc's cross-jumping (`tails = "shared"`), and the routine's jump word.
- **A dispatch on a number** (`dispatch`, a jump through a table on the direction code) is an if-chain over 0 to 7. The code for 7 ends the outline; its arm writes the end and breaks out of the loop. A Network loop's exit is an `if` with an arm that ends in `break`; the arm may run things first.
- **A loop with two entries** (`ocj` reads the next outline word and falls into `och`, which reads the next code) is one loop over codes that reads the next word at its end. The statements before the loop and at the end of its last `if` are the same; `runsc` lays them out once.
- **The outlines themselves** are data on the tape: a Record whose field gives each slot its own initial value, one line a slot. In RUNS they are part of the source; conceptually they are an asset (AEMS).

The heavens add four:

- **A macro with arguments laid out once a run, with words of its own** (`dislis J, Q, B`, once a magnitude) is a Processor with parameters, `show_magnitude(m, first, past, intensity)`, run four times with constants. What each copy keeps of its own (the homes of `star_x` and `star_y`, the scan's start `fpo`, the cursor `flo`) is the declarations': the locals are each copy's, and the cursor is the slot `m` of `magnitudes.cursor`.
- **A value held in an instruction and compared as one** (`fyn, lio .`, then `idx fyn / sad (lio Q+2`; `fpo, lio`, then `sad fpo`) is a place in the catalog, a local word in RUNS: `star_y == past`, `star_y == scan_start`. That the comparison is of `lio` words is the declarations'.
- **A jump into a run of copies** (`bjm, jmp .` into `bds`, 16 dots, past as many as a random number says) is a counted loop from a local, `for dot in skipped .. 017`. The declarations lay it out as the jump (Duff's device).
- **A program flag a routine clears, then sets and tests** (flag 5, a star was plotted; flag 6, the line's mirrored half) is a local of an enum (`scan`, `half`): each routine clears it before it reads it, and nothing reads it after. The declarations hold it in the flag.

The star catalog is data on the tape: a Record, `star_catalog`, whose one field takes a value a slot, written as the source writes each star (`8192 - 1537`, `371 << 8`, from `mark 1537, 371`). Conceptually it is an asset (AEMS). Where it lies (`6077/`) is layout: nothing but the planetarium names it, and it reads the catalog through its own places. It lies right after the free core the outlines' code takes, 02105 words (`[code_words]` in `pdp1/main_loop.toml`), which `runsc` reserves after the object table; the catalog follows them, so another size builds another image. The compiler writes 0132 strokes, 684 words.

## What the conversion showed

**The 1962 program is already shaped like RUNS.** The object table is a Record collection. Each calc routine is a Processor. The routine word in each slot names the rule that runs the object, which makes it a state. The main loop's jump through that word is a guarded dispatch on that state. The tunables that the original keeps as instructions to execute (`the`, `hd2`, `hr1`, and others) are the authors' own swap points.

**The Network holds gameplay, not plumbing.** The main loop decides who collides with whom and when. Object *i* is tested against every later colliding object and can explode both. Then *i*'s calc routine runs, in the same frame, on the changed state, before *i+1* is touched. The last slot is never tested and never counted. These are rules of the game. Moving the collision test into its own phase after all objects move, as an earlier conversion did, changes 294 of 300 test frames (`tools/check_frame.py` on a variant of the frame Network). The arcs carry this order: in `runs/frame/active_object.net` the collisions give the table to the place `collided`, and `calc` takes it from there.

**Firing is parallel where nothing orders it.** Two Processors that touch one place are ordered by a wire or a guard; any others may fire in any order or at once (EGS CONTEXT.md, Network). The evaluator lowers each network file to one sequential order the wiring allows.

**The machine falls away where play does not reach it.** Each PDP-1 device in the original maps to a RUNS form:

| In the original | In RUNS |
|---|---|
| Cursors kept in instruction address fields | The Network's slot index |
| `jsp` and `jda` calls, `xct` of a tunable, a macro | `run` a Processor or a sub-Network |
| Values in AC and IO | Locals inside a Processor; between Processors, a field of `handoff` |
| A routine's own scratch words (`sq1`, `mxc`) when they pass between Processors | Record fields |
| The routine word's address plus its sign bit | An enum, and a guard that compares it with `explosion` and `in_hyperspace` |
| The scores and game count core held at power-on | Fields with no initial value, declared by the top Networks |
| `hlt`, showing the scores, then reading the switches again | A Processor's `emit scoreboard`, then the Network's `wait` |
| Code the program writes and then runs | a collection of commands (data) and a walker over it; the declarations hold the collection as code |
| A shift instruction built at run time and executed | A shift by a counted number of places |
| IO left over from the main loop in `in_hyperspace` | `handoff.jump_low`, which the draw shifts out (checked: SIMH runs each call with a random IO) |

The cursors are layout the program uses but play never observes; `tools/reach_oracle.py` counts 54 of them.

**Exactness is about the game, and placement is about the machine.** The conversion keeps every word that carries meaning from one routine to another or from one frame to the next. That includes `objects_seen`, which is counted and never read, as a Record that no Processor reads. The graph shows that it is dead. A value that one Processor sets before it reads it and never hands on becomes a local, such as the dot's coordinates in `plot_particle`. Machine-only words such as `mas`, a cursor that is stepped and never read, drop out. To rebuild the exact binary, a compiler needs a second artifact, the PDP-1 declarations (`pdp1/`, which `tools/runsc.py` compiles with the RUNS source). The declarations place Records in core, encodes enum values as words, and lays out the scratch. It holds only what play cannot observe.

## The language

The RUNS spec states the language (`../runs-spec/NETWORK_TOPOLOGY.md`, Network files; `DIGS_EXPRESSION_LANGUAGE.md`). Spacewar's source uses: Records in `.runs` files with typed fields and initial values (a field with no initial value comes in from the world); one Processor per `.runs-prim` file with `in`/`out`/`inout` lines; one Network per `.net` file with `places`, `transitions` and `arcs`, guards written `when <test>` and closed by `when else`; loop bundles with a `counter` line; `requires:`/`produces:` on top Networks; `stop` where the machine halts; enums that may share a member's name; and `word`, Spacewar's number: 18-bit ones' complement, declared in the RUNS source. Add and subtract wrap with end-around carry; a word compares with 0 by its sign, and `==` compares all 18 bits. It is a rule: another arithmetic is another game.

## Decisions that other games force

A swarm stress-tested this draft against Super Mario Bros., DOOM, Ocarina of Time, Journey and an Unreal Engine game (the analysts worked from memory of those games; their claims are not checked). Where it stands:

| Question | Where it stands |
|---|---|
| What comes into the game | Inbound boundary Records (EGS CONTEXT.md, Boundary Record), named by the top Network's `requires:`. |
| Arithmetic in guards | Not allowed: a guard reads a precomputed fact, and a Processor computes it into a Record first (EGS CONTEXT.md, Phase / Dispatch / Guard). |
| Call syntax | None: a Processor never calls another Processor; Processors connect through Records in the Network, and composition is bundling (EGS CONTEXT.md, Network). The source has none. |
| Layout | Stated in the source where play reads it; the declarations hold the rest. |
| Crashes and hangs the original reaches | Rules. |
| Objects made and freed at run time, and references to them | The game's own allocator is converted. A stale reference does what the stated layout says. |
| Recursion | Open. A stack that overflows is layout. |
| Floating point | Types of the original machine, as `word` is. Library math is code, converted as Processors. |
| Assets | AEMS, a separate protocol. |
| Versions | Each version is its own game. |
| Code with no source | Converted from its machine code. |
| Running data as code | Commands as data and a walker in the source; the declarations hold the commands as the walker's code (`held_as_code`). Spacewar's compiled outlines are the case. The evaluator still parses `type insn` and `jump`, which no program here uses. |
